# SR1 decisions

## 2026-10-13: authority and open decisions

On 13 October 2026, Adrian handed SR0 and SR1 to the Claude session "swiftright-87". His words: "carry on" and "you have permission to do whatever it takes to move the project forward". The session made the decisions below under that grant. Each one can be reversed if Adrian says so.

1. **ABI 0.7 (additive) is approved.** The 0.6 table, layouts and behaviour stay unchanged. 0.7 appends entries only, starting with font-resource registration (`factory/abi/abi-0.7-proposal.md`, section "Private custom-font obligation"). Renderer work starts once tuple 12 qualification no longer depends on the renderer bytes, so that the pinned tuple 12 DLL is never rebuilt mid-qualification.
2. **The Windows default body font is Segoe UI, not a copy of the Mac font.** SF Pro is licensed for Apple platforms only, so it cannot ship on Windows. Exact glyph pixels for `Font.body` therefore cannot match. Text cases are judged on semantics instead: line count, truncation and ellipsis, frame and bounds, colour, and alignment. Glyph pixels are reported but do not gate. A tolerance is never applied silently: each comparison report names the text regions it excludes from the pixel gate.
3. **SF Symbols are not redistributed; the Windows provider maps them onto Segoe Fluent Icons.** The SF Symbols licence is also limited to Apple platforms. `Image(systemName:)` is judged on frame, aspect-fit, tint and content bounds, and the glyph-shape difference is reported. Exact symbol shapes would need an open-licensed symbol set that we author ourselves; that is a separate future block.
4. **Lean loop.** New captures use `factory/tools/pair.py`: build, capture, then an exact RGB diff with a plain JSON report. Earlier receipt machinery is archived as history and is not required for new evidence.
5. **Shape edges allow a bounded anti-aliasing difference.** CoreGraphics coverage anti-aliasing and the GPU rasterizer used by GPUI cannot produce identical edge pixels. Geometry, position, size, interior colour and every non-edge pixel must still match exactly. A pixel within 1 px of a shape edge (an edge band derived from the Mac image) may differ by at most 32/255 per channel. `pair.py` reports the gate as "exact" or "edge-AA ≤32", and gives the counts on its own line. Glyph regions follow item 2.
6. **The W08 repair guard lives in RightKit; SwiftRightBridge consumes a pinned copy.** The handover made RightKit the owner of the repair-helper design, so the canonical script is `rightkit/packages/release/msix-repair-guard.ps1` (with `msix-repair-guard.mjs` returning its text and sha256, and a unit test). SwiftRightBridge embeds a byte copy (`guard/msix-repair-guard.ps1` -> generated `RepairGuardScript.swift`); `guard/rightkit-pin.json` names the RightKit commit, package version and sha256, and a SwiftRightBridge test fails if the embedded script and the pin disagree (and, when the RightKit checkout is present, if it differs from the canonical file). RightKit changes the file; SwiftRight re-pins with `node tools/gen-repair-guard.mjs --sync <rightkit> --commit <sha> --rightkit-version <v>`. No RightKit version is bumped or published here: the bump goes through the Rightkit Mac session, and the pin says `+unreleased` until then. This supersedes the 71aa269e0 commit message ("placed in the SwiftRight runtime rather than RightKit").

7. **The Windows Toggle is drawn from our own vector model, measured from SwiftUI on macOS.** Windows has no SF switch or checkbox artwork and Apple's is not redistributable, so `SwitchArtwork` and `CheckboxArtwork` in `SwiftRightHost` draw both from numbers measured on Mac renders at scale 2.5: end-cap outlines, flat state colours (light appearance), the knob's soft shadow, the check-mark strokes and a disabled edge-coverage curve (`factory/tools/switch-artwork/derive_*_profile.py`). No pixels or assets are copied. Metrics, in points: switch 54 x 24 with a white 32 x 20 knob inset 2 (trailing when on) and its label 8 before it; checkbox 16 x 16 with its label 4.8 after it (a labelled box sits 0.8 low, as AppKit sets it). Colours: on (0,120,249); off 230; disabled on (75,157,247) for the switch and 236 with a 175 check for the checkbox; disabled off 242. The gate for an unlabelled control is frame exact, flat colours exact, shape edges and the shadow gradient within edge-aa 32 (decision 5). A labelled control's label text follows decision 2 (Segoe UI is narrower than SF, so the switch sits a few points left): `factory/tools/pair_control_report.py` then requires the control itself to match after translating by the label-advance difference (same size, exact flat colours, edge-aa 32) and the label's vertical centre within 3 px, and it reports the shift and the label pixels. Dark appearance is not measured: the resolved tree carries no colour scheme, so a Toggle in a dark environment is still painted light (known gap).
8. **The Mac default Toggle style is a checkbox, not a switch.** `Toggle` with no `.toggleStyle`, `.automatic` or `.checkbox` renders an AppKit checkbox; only `.toggleStyle(.switch)` renders the switch. The runtime therefore lays out and paints the default style as the checkbox, and `.switch` as the switch. Before this the runtime gave a Toggle no intrinsic size and the host had no Toggle paint, so `LabelsHiddenTests` and `ToggleLayoutTests` now expect the control's size.
9. **Mac references for AppKit controls come from an offscreen NSHostingView.** `ImageRenderer` cannot draw AppKit-backed controls (a switch becomes the yellow "prohibited" placeholder). The control cases use `factory/pipeline/blocks-6-10/shared-mac-host`: the witness is hosted in a borderless window that is never ordered onto a screen, so nothing appears, nothing takes focus and no permission is asked. AppKit draws controls inactive (grey) in such a window, so the window subclass answers the private `hasKeyAppearance` selector and reports the capture scale as its backing scale. This is a capture-tool technique, not product code, and applies to scale 2.5 only.
10. **`.disabled` dims controls, not plain views.** Measured on macOS: a plain `Text` or shape under `.disabled(true)` renders byte-identical to the enabled view, while a Toggle switches to the disabled colours above (and the label stays as is). The runtime already blocks activation and publishes `isEnabled`; the host now paints the disabled colours and sets the UIA disabled flag. The plain-view claim is covered by `swiftui.disabled/plain-disabled-v1` and `plain-enabled-v1` (Text, RoundedRectangle, Circle under `.disabled(true)` and not): both pass against the Mac, and the Windows captures of the two are byte-identical in all 20 runs. `Button` is decision 11.
11. **The Windows `Button` is our own vector model, and Text takes a foreground colour.** SwiftUI's default `Button` on macOS is a bordered push button. The runtime lays it out as its label plus 12 pt on each side and 4 pt above and below (measured with `NSHostingView.fittingSize`: `Button("Run")` is 48 x 24 pt; a 30 x 10 pt view label gives 54 x 18); there is no `buttonStyle` in the runtime yet, so every Button is this style. `ButtonArtwork` in `SwiftRightHost` draws it from numbers measured on Mac renders at scale 2.5 (`factory/tools/switch-artwork/derive_button_profile.py`): the corner outline (about 7 pt), flat fill 235 enabled and 245 disabled, label colour 36 enabled and 182 disabled (light appearance only, like decision 7). The label is the Button's child Text; it takes the button's label colour unless it sets its own. Text with a foreground style now paints: the host re-shapes the measured run in that colour (colour is baked into a renderer run, geometry is unchanged), so `foregroundStyle(Color.red)` needs no renderer change. A button is as wide as its label, which is narrower in Segoe UI (decision 2), so its gate is `factory/tools/pair_button_report.py`, not exact pixels: same height and y; the two 28 px end caps, each aligned at its own edge, exact on flat colours with edge-aa 32; the straight top and bottom bands flat fill; the label centred and its darkest ink within 40/255 of the Mac's; the width difference reported. Text colour is gated by `factory/tools/pair_textcolour_report.py` (strongest ink pixel within 24/255 per channel), and the glyph pixels stay excluded and named (decision 2).
12. **Where a TextField's text starts is gated, in pixels, with a numbered rule (14 October 2026, closing an Oracle finding).** What was wrong: `TextFieldMetrics.bezelTextInset = 4` put every bezeled field's text about 2 pt (5-7 px at scale 2.5) left of macOS, and no gate saw it: the static cases excluded the whole text rect from x = 35 and the interaction cases were semantic-only. Measured: `NSTextFieldCell.drawingRect(forBounds: 120 x 24)` is (4, 4, 112, 16) (regular, small and mini control sizes, rounded and square bezel alike), which is the 4 pt that sets the ideal width (`cellSize` of "Hello" is 43 x 24 = text + 2 x 4); the field editor's `NSTextContainer.lineFragmentPadding` is 2 pt more, so the text STARTS 6 pt in (`factory/tools/appkit-probe`). The Mac captures agree: the selection highlight starts at x = 40 px (frame 25 + 15). The runtime now keeps `bezelTextInset` = 4 for layout and the clip and adds `bezelTextOrigin` = 6 for the text origin and the caret (the plain field has neither). The right-hand clip is not settled and not gated: for `Hello, a long sentence...` in an 80 pt field the Mac cuts a glyph at 4 pt from the edge (last ink column 214 in a frame ending at 225), for an unspaced `HelloLongSentenceThatWillNotFit` it ends on a whole glyph at 6 pt (210); the runtime keeps the old 4 pt clip. The selection highlight is `NSColor.selectedTextBackgroundColor` in the aqua appearance, emphasized: (0.7020, 0.8431, 1.0) = (179,215,255) over white, the accent (0,122,255) at 30%, which is what the Mac captures draw (the host window answers `hasKeyAppearance`); the Windows host had (153,201,239). Unemphasized (a window that is not key) is (220,220,220) and darkAqua emphasized (63,99,139); neither is painted (light, key-appearance only, like decisions 7 and 11). THE RULE (`factory/tools/pair_textorigin_report.py`, run beside each case's deciding gate through `"textOriginGate"` in pair.json): glyph shapes stay excluded (decision 2), but on the final frame of every run, for every field frame the case names, (a) the first ink column (the leftmost column with a pixel more than 32/255 darker than the darkest background colour present, the AA band of decision 5, caret columns removed) must be equal on both sides within `firstInkTolerancePx` (default 0; a non-zero value must be measured and carry `firstInkToleranceReason`; none is used: every case measured a difference of 0 px; `filled-truncated-v1` first showed 1 px with a leading 'A', whose diagonal foot crosses the 32/255 threshold one column apart in SF and Segoe UI while the stem edge of an 'H' matches to the pixel, so its text now starts with 'H' instead of the gate being loosened); (b) a selection highlight present on one side only fails; where both draw one, its colour must be identical and its start column (the leftmost column with at least 10 pixels of that exact colour) equal within `selectionStartTolerancePx` (default 0); its end and height follow the glyph advances and the line height and are reported only; (c) with `"caret": "macFact"` the Windows caret column must equal the Mac insertion point read from the field editor (`MAC_FACT caretXpx`, because AppKit draws no caret in a window that is never on a display) within `caretTolerancePx` (0), for a caret at the text origin (`textfield/caret-empty-v1`); a caret after typed text follows the glyph advances and is reported only. The gate applies to the static cases (placeholder, prompt, automatic, filled-truncated, plain) and to the interaction ones (submit, the four focus-state cases, the four ime-marked-text cases) alongside their semantic gates. Not gated, stated: marked text is a yellow background on the Mac and an underline on Windows, and its start follows the glyph advances; the focus ring is not drawn on Windows. `tab-order-v1` now ends on a Tab: its earlier final step was a synthetic click on a field that was already editing with its whole text selected, where the Mac harness leaves the selection (AppKit's text system does not collapse it for an event we post) while Windows places the caret as macOS does; that click stays as the semantic phase t4 and the final frame shows the Tab-focused second field on both sides. Correction to B3 below: "text 4 pt in" is the cell inset; the text starts 6 pt in.
13. **A Mac switch is redrawn after a click so that the capture shows what the accessibility tree says (14 October 2026).** In the offscreen host, `derived-click-v1` captured the derived switch ON with "count: 0" while both accessibility trees said OFF. The Mac capture was stale, not the runtime: SwiftUI's switch is an `AppKitSwitch` hosting view inside `NSSwitch`; after a click `state` is already new (AX value 0, one binding setter call) but its knob and track layers keep the pre-click position (knob x 20 instead of 2) because the redraw follows a display-link animation that a window that is never on a display never ticks, and no amount of waiting (3 s measured), layout, display or CATransaction flush changes that. A programmatic flip of `state` and back, with a run-loop turn after each, redraws it (it sends no action: the setter ran once per click). `settleSwitches` in the Mac host (template and `derived-click-v1`) does that after the steps; it is a no-op without switches. `derived-click-v1` therefore gates pixels now (edge-aa 32 outside the named `count: 0` glyphs) as well as the semantic tree.
14. **A TextField's text is gated in y as well as x (15 October 2026, closing gap 3 of the mutation calibration).** What was wrong: decision 12 gated where the text starts across the page, and nothing read where it sits down the page, so text 2 pt (5 px) too low passed (`to-filled/centring-y-2pt`). `pair_textorigin_report.py` now also measures, on both sides, `firstInkY` (the topmost ink row of the FIRST GLYPH: the run of consecutive ink columns from the first ink column) and `baselineY` (its lowest ink row). The first glyph is used so that nothing after it can move the measure: a marked-text underline, a taller later letter, or a different right-hand clip (all seen). Measured over the 20 runs of every textfield, focus-state and ime-marked-text case (Windows minus Mac, px, constant across runs): (firstInkY, baseline) is (2, -2), (2, -1), (1, -2) or (1, -1) in the bezeled fields and (1, 0) in the plain one. Windows draws the body font at 12 pt and the Mac at 13 pt (decision 2), so the glyphs are shorter; with the line centred on both sides the top sits lower and the baseline higher. Gated: |firstInkY delta| <= `firstInkYTolerancePx` (2; plain-v1: 1), |baseline delta| <= `baselineTolerancePx` (2; plain-v1: 0) and |mid-point of the two deltas| <= `inkCentreYTolerancePx` (0.5), each default 0, each non-zero value in the case's pair.json with `yToleranceReason`. A 5 px shift fails every check in either direction; a 1 px shift fails the mid-point check unless it lands on another measured case's value.
15. **The IME marked range, the selected range and the composed string are gated per step (15 October 2026, gap 1).** The accessibility trees carry the text only, so a wrong marked range on either side passed (`sem-ime/marked-range-windows`, `marked-range-mac`, `marked-lost-windows`). `factory/tools/pair_ime_report.py`, run through `"imeGate"` in pair.json beside the semantic and text-origin gates of the four ime-marked-text cases, parses the Windows `HOST_FIELD tag=script` lines (one per scripted step) and the Mac `MAC_FACT` lines after `step=start` (one per click or ime step) and compares, for the Nth step and again for the settled final state (the last HOST_FIELD line against the last MAC_FACT line): the marked range (an empty Mac range, which AppKit leaves after a click or a commit, equals Windows `none`), the selected range, and the composed text. A different step count, a missing log or a missing line fails. The Windows log is written in the console code page, so a non-ASCII character is several unrelated bytes there (`ab` plus U+4F60 reads `abS+` and a byte): an all-ASCII Mac string must match exactly, one with non-ASCII must match up to its first non-ASCII character and Windows must continue beyond it; the exact characters are compared by the semantic gate on the UIA values. Real runs: every step of every ime case already agreed.
16. **A labelled Toggle is gated in x, and its label centring is 1 px (15 October 2026, gap 4).** decisions 7 and 9 translated the control by the label-advance difference and gated only its size, y and edges, so a control or label 2 pt off in x passed (`ctl-switch` and `ctl-checkbox`: `label-origin-2pt-x`, `control-x-2pt`). `pair_control_report.py` now also gates, per run: the row's leading edge (the leftmost ink: the label for a switch, the box for a checkbox) within `leadingXTolerancePx` (0); the label's first ink column within `labelLeadingXTolerancePx` (0); both sides put the label on the same side of the control; and the ink-to-control gap (the label's ink edge nearest the control to the control's edge) within `controlGapTolerancePx`. Measured: the checkbox row starts at 0 and its label at 54 on both sides with a 14 px gap; the switch's label starts at 2 on both sides and its gap is 23 px on the Mac and 22 on Windows (the right side bearing of the label's last glyph, Segoe UI vs SF), so the switch carries `controlGapTolerancePx: 1` with `controlGapToleranceReason` and the checkbox 0. The label's trailing edge is never gated. The label's vertical centre measured 0.5 px on every run, so `labelCentreTolerancePx` goes from 3 to 1 (tightened, with `labelCentreToleranceReason`).
17. **The alert's default button and the main window's layout are gated statically (15 October 2026, gaps 5 and 6).** (a) `defaultButton` (a new field in `semanticGate.fields`, listed in all nine alert cases): UIA cannot report the default (keyboard focus is false in the Sandbox, D7) but the Windows host log records what it asked the TaskDialog for, `HOST_DIALOG_REQUEST ... buttons=A|B|C default=<index>`, and the Mac AX dump marks `default` and `cancel` on its buttons. The Nth request is compared with the Nth dialog: the requested default must be the Mac's default button; when the Mac has none (D5: the first button is the cancel or destructive one) it must be the Mac's cancel button, so the destructive action is never the default; a missing request, a missing index or an index out of range fails. All nine real alert runs already agreed (three-buttons First, default-enter Save, confirmations Cancel). Enter still gates the behaviour (default-enter-v1). (b) `boundsY`: y and height of every kept main-window element within `boundsYTolerancePt` (0.05); measured 0.0 on every element of every committed run of every semantic case. `boundsX`: x of the roles in `boundsXRoles` (textfield, switch and the leading-aligned texts) within `boundsXTolerancePt` (0.05), measured 0.0; `boundsCentreX`: the centre x of the roles in `boundsCentreXRoles` (the centred button and texts) within `boundsCentreXTolerancePt` (0.25; a push button measured 0.2), because a centred element's left edge and every width follow the label's advance (decision 2) and are not gated. Dialog windows are not compared in position (a TaskDialog and an NSAlert share no layout). Still not gated, by D7: the UIA keyboard-focus flag.
18. **The clock gate checks where the edges are, not only how wide the bar is (15 October 2026, gap 2).** C2 gated the extent (width) within 1 px and left a 3 px strip around every differing edge out of the exact pixel comparison, so a bar translated 2-3 px with its width unchanged passed (`clk-linear/bar-translate-x-2`, `clk-move/translate-x-2px` and `-3px`). `pair_clock_report.py` now also gates, per tracked shape and frame, the position of the LEADING and the TRAILING edge, each read as a coverage-integrated position in capture px, within `edgeTolerancePx` (default: the case's `extentTolerancePx`: 1 px; the springs 2 px). The strips stay, for anti-aliasing only. Measured on every committed clock run: the leading edge differs by 0.000 px in every frame of every case; the trailing edge by at most its extent difference (0.47 px animation-value, 0.50 linear-width, 0.29 easeInOut, 0.42 interrupt, 0.00 move-leading, removal-move). A 2 px translation therefore fails the 1 px cases, and a 3 px one fails the spring's 2 px. The leading edge could be tightened to 0.5 px on the evidence; it was left at the named tolerance. A missing capture now fails its pair instead of crashing the comparator before it writes its report.
19. **A Text line's position is gated, and a text gate also gates its ink colour (15 October 2026, gap 6).** The text-colour cases (Text, borderless and plain Button labels, dark Text) excluded the glyph rect from the pixel gate (decision 2) and gated only the strongest ink pixel's colour, so text 2 pt off in x or y passed (`tc-red`, `tc-fg`, `tc-dark`). `pair_textcolour_report.py` takes `"position"` in `textColourGate`: per region the ink is the pixels at least 15% of the strongest ink's contrast from the region's background (relative, so an ink colour moving within its 24/255 tolerance never moves the edge it is measured at), and the first glyph's top and bottom and the ink bbox are compared as in decision 14 (top 2, baseline 2, mid-point 0.5) plus x: for centred text the centre of the ink bbox within `inkCentreXTolerancePx` (1.5), for leading text (`text-dark-v1`) the first ink column within `firstInkXTolerancePx` (0). Measured over the committed runs of all ten cases (17 regions): top +1..+2, baseline -1..-2, centre x -1.5..+1.5, leading x 0. The text-gate case (Tinos, same font bytes on both sides, ink bbox gated within 1 px) had no colour gate, so a dark-red ink passed; `textColourGate` now runs beside it (measured strongest ink 39 on the Mac, 31 on Windows). `pair.py` runs `textColourGate`, `textGate`, `textOriginGate` and `imeGate` beside whichever gate decides.

## 2026-10-13: round 3, lane C (blocks 18 swiftui.animation and 19 swiftui.opacity-transition): animation facts and decisions

Everything below was measured on macOS 27 (Xcode 27 RC) SwiftUI, either through the manual clock (F1) or a real-time probe. Each fact has a unit test in `probes/sr0-s/fresh-runtime/Tests/SwiftRightRuntimeTests/AnimationMeasuredTests.swift` and, where a pixel case exists, a paired case under `factory/pipeline/blocks-6-10/swiftui.animation/` or `swiftui.opacity-transition/`.

C1. **F1, the manual clock, evaluates SwiftUI's own animation, not a static stand-in.** The case's `Witness.swift` is byte-identical on both sides and builds its animations through `FactoryAnim.wrap(_:)` and its timed events through `FactoryClock.at(t) { ... }`. Windows (`CaptureHost.template.swift`, env `SWIFTRIGHT_CLOCK` and `SWIFTRIGHT_FRAME`): one host launch per clock step; the host ignores display ticks and, on its first tick, calls `Graph.tick(now:)` at `clock[0] ... clock[k]` in order (flushing after each; an event that fires at a step flushes and ticks again at that time so its motion begins there), then holds step k for the PrintWindow capture and prints `HOST_GEOMETRY` (every node's presented frame and opacity). Mac (`MacClockHost.template.swift`): `FactoryAnim.wrap` returns a `CustomAnimation` that forwards to the ORIGINAL `Animation` (`Animation.animate(value:time:context:)`, public since macOS 15) with `time` read from a clock the host moves; SwiftUI's own render loop drives an `NSHostingView` in a never-shown window, so the curve, merging and completion are SwiftUI's. The host moves the clock, waits until SwiftUI has evaluated the new time, and `cacheDisplay`s. `pair.py` takes the clock from `pair.json` (`"clock"`) or `--frames`; every (run, frame) is one pair; `pair_clock_report.py` is the gate. No GUI is involved on either machine.
C2. **The clock gate.** SwiftUI draws a fractional edge anti-aliased; the runtime snaps presented frames to the device pixel grid (`DevicePixelSnap`), so an animating edge differs by up to 1 px of extent and one partial-coverage column. Per (run, frame) the gate requires: (a) extent, the coverage-integrated width of the tracked shape on both captures, within 1.0 px; (b) every pixel identical outside 3 px strips around the tracked edges that are not on a whole device pixel on the Mac (the strips are counted in the report; frames whose edges sit on whole pixels are fully exact); (c) progress, SwiftUI's own progress at that step (from the wrapper log) against the runtime's presented frame, within 0.004 (snapping alone explains 0.5 px over the travelled distance). Cases without a moving geometric edge (opacity, move at quarter steps) are plain exact pixels.
C3. **The curves are CSS Béziers, not quadratics.** `easeIn`, `easeOut`, `easeInOut` are cubic Béziers (0.42, 0, 1, 1), (0, 0, 0.58, 1) and (0.42, 0, 0.58, 1): identical to `UnitCurve.easeIn/easeOut/easeInOut` and to the values SwiftUI returns (0.129162 at 25 %, 0.870838 at 75 % for easeInOut; 0.315357 and 0.684643 at 50 % for easeIn/easeOut). `Animation.linear/easeIn/easeOut/easeInOut` without a duration last 0.35 s. The old runtime used quadratics and a 0.35 s easeInOut as `.default`.
C4. **`Animation.default` is a 0.5 s spring without bounce; it equals `.smooth` and `.spring`.** It is not a closed-form spring: SwiftUI integrates in small fixed steps (the value is constant over 3 ms runs) and its result also depends on how often it is sampled (0.3 s reads 0.890036 when sampled 0.1 s apart and 0.886455 after dense sampling), so no analytic spring fits (best critically damped fit: worst error 0.0097). The runtime therefore tabulates the curve sampled at 12.5 ms steps from a fresh state (`SpringModel.table`) and interpolates; at the 0.1 s cadence the cases use it matches SwiftUI to 6 decimals. SwiftUI removes the spring at 0.537 s (the first call that returns nil) and the value snaps to the target; its logical duration is 0.5 s.
C5. **Interruption is additive, not a restart.** A second animation on a node whose first is still running starts a second layer; the first keeps running to its own end. Measured (the first animation's `value` stays 100, the second's is `target_2 - presented_1(t)` each frame): `presented_j(t) = lerp(presented_(j-1)(t), target_j, curve_j(t - start_j))`, which for 100 -> 200 interrupted at 40 % by 200 -> 100 is `100 + first(t) * (1 - second(t - 0.4))` (148 at 0.6 s linear, 140 at 1.0 s, 100 at 1.4 s). The old runtime restarted from the presented value. A built-in spring that interrupts a spring is the exception: SwiftUI merges them (`shouldMerge` is true) and the new spring continues from the presented position and velocity; the runtime approximates that with a critically damped continuation (omega 12.658) and does not gate it.
C6. **Completion.** `.logicallyComplete` (the default) fires at the animation's logical duration (linear 0.5 s: 0.5004 s; default spring: 0.5 s although it settles at 0.537 s); `.removed` fires when the animation has been removed from the presentation (linear 0.5004 s; default spring 0.537 s; an interrupted pair: both at 1.4 s). An interrupted transaction therefore completes at its own end (1.0 s), not when it is interrupted. A change that changes nothing and a nil animation complete at the commit. A transaction started no layer: completion at the commit.
C7. **`.animation(_:value:)` is scoped and beats `withAnimation`; `Transaction.disablesAnimations` silences only the modifier.** The modifier applies to the nodes below it, only in the update in which its value changed; the innermost one wins over the explicit transaction (`withAnimation(.linear(1))` over `.animation(.linear(2), value:)` runs 2 s; a `nil` modifier snaps an explicit animation). A transaction with `disablesAnimations` and no animation of its own makes the modifier yield (the change snaps); with an animation of its own it still animates. `withTransaction(_:_:)` is new. Known limit: when several `withAnimation` blocks run before one flush, the last decides for every changed node (state changes are not attributed to individual blocks).
C8. **`onAppear` runs after the view's first render.** SwiftUI presents the initial state, then runs the action, and what it changes is a second update, so `onAppear { withAnimation { ... } }` animates from the initial state and does not fade the view in. The runtime used to run appear actions during evaluation (the first commit already showed the final state, and the whole tree faded in). `flush` now presents the state the new nodes first appeared in, then runs the pending actions (an `onChange` evaluated after a pending appear waits behind it, so the measured order is kept) and commits again if they changed anything. A flush with no `onAppear` is unchanged.
C9. **Transitions.** A view inserted under an animated transaction starts from its transition's initial state and animates with the transaction's animation: `.opacity` (also the default for views without a `.transition`) alpha = progress; `.move(edge:)` shifts by the view's own size towards that edge (leading: x = final - width * (1 - progress), no fade); `.offset`, `.slide` (leading in, trailing out), `.identity` (no animation), `.asymmetric`, `.combined(with:)`. The transition belongs to the inserted subtree's top; every node of the subtree takes the same initial state. A removed view under an animated transaction stays in the resolved tree as a ghost, frozen at its last frames, while it fades or moves out (measured: `.opacity` removal alpha = 1 - progress; `.move(edge: .leading)` removal moves by -width, `.slide` removal by +width; siblings relayout at once), then leaves; its transaction waits for it. Not delivered: `.scale`, `.blurReplace`, custom `Transition` conformers, `matchedGeometryEffect`; a removal ghost keeps its subtree's frames, so a ghost of a view whose siblings keep animating does not follow them.
C10. **Opacity.** `.opacity(_:)` multiplies down the tree (0.5 over 0.5 is 0.25) and animates like any value. Rects and colours fill with the node's alpha (exact on the Mac: 8-bit alpha over white). F2. **`lineLimit(n)`, truncation and run lookup (block 28, gaps R4, R5, R9, R6).** `lineLimit(n)` for n >= 1 measures the longest prefix plus an ellipsis that fits n lines (`SingleLineText.select(lineLimit:)`; macOS wraps at words and ends the last line with "…", measured). When not even the ellipsis fits the offered width the old code threw `noCandidateFits` and ended the page; the host now measures the ellipsis alone (it overflows the offer by its own width; macOS instead clips the first glyphs: not reproduced, known difference at widths under about 10 pt). A text whose snapped bounds are one pixel shorter than its measurement (a half-device-pixel origin or height: a baseline-aligned row, an odd offset; decision E12) is no longer refused: a measurement within 1 px of the bounds on each axis is the run (`RetainedRunChoice`), the closest wins, anything further is still `measuredRunGeometryMismatch`. The retained-measurement bound is 8192 (was 256; a settings page measures 900). A node identifier over 256 bytes (the renderer's `SWR_IDENTIFIER_MAX`; the hub's tree reaches 500) becomes its first 180 bytes, "~" and a 16-digit FNV-1a hash (`SemanticIdentifier.fit`). `TextMeasureError.description` no longer calls itself (the first measurement failure overflowed the stack).

F3. **Baseline alignment (block 33, gap G12).** `VerticalAlignment.firstTextBaseline` and `.lastTextBaseline` in an HStack line up the children's first (or last) text baselines; a view with no text counts its bottom edge. Measured: padding and frames carry the baseline of their child (a frame places it by its alignment), a VStack passes up its first child's first baseline (its last child's last), an HStack the topmost (lowest) of its children's, a wrapped text's last baseline is its last line's. In a ZStack, overlay or frame alignment the two values centre. The gate is a relation on EACH side separately (`baselineAlign` in `pair_textcolour_report.py`: every item's baseline, a text's first-glyph bottom or a shape's bottom edge, within 1 px of the first item's), because Segoe UI and SF have different ascents and an across-platform position gate would test the fonts.

F4. **Large-radius continuous shapes (block 30, gaps R7, R8).** A continuous `RoundedRectangle` radius is clamped to min(w, h) / 2 (r = 20 and r = 99 give the same path on 100 x 40) and between the extent limit r0 = half / 1.5287 and half the first cubic of each edge starts at the edge's mid-point with control distances from the corner that move linearly in r: outer 1.0885 r0 -> 0.96 half, inner 0.8684 r0 -> 0.82 half (fits every measured radius on five rectangles to 5 decimals; the path equals `RoundedRectangle.path(in:)` to 4 decimals in a unit test). A shape over the rasteriser's work limit (a card at 2.5x is 3.4 Mpx) is drawn as horizontal bands that abut exactly (`ContinuousRoundedRasterizer.rasterize(bandTop:)`; unit test: bands stitched equal the whole raster); a shape with no area draws nothing. The fill's anti-aliasing is NOT Apple's on the flat shoulders of a large-radius corner: our raster equals the exact coverage of the path (an independent 24 x 24 supersample in Python agrees to 1 level), SwiftUI's own fill of the shape and of `Path(path(in:))` are identical, yet Apple's coverage differs by up to 196/255 in the 1 px edge band there. Those cases carry `edgeAATolerance` (new in `pair.py`, a named reason is required, never loosens the exact gate outside the band): 210 for pills, 130 for radii between the limit and half, 220 for their strokes. Not delivered: the stroke of a pill (radius near half the short side): SwiftUI's stroker draws short ticks across the path at the points where the straight segment collapses (a vertical tick at each end of a stroked pill, at each pole of a circle); the fill is exact.

F9. **`TextField(_:text:axis:)` (block 34, gap G17).** Accepted and drawn as the single-line field (same frame, placeholder and text origin as the Mac for an empty or short field: measured 120 x 24 rounded, 120 x 16 plain). ## 2026-10-15: round 5 block 35 (image from data)

F17. **`Image(decorative: RGBAImage, scale:)` draws decoded pixels (round 5 block 35, hub gap: app icons).** `RGBAImage` (runtime, `Controls.swift`) is width, height and straight-alpha RGBA8 bytes (top row first, no padding) with a content id: a 64-bit FNV-1a of the dimensions and bytes, equal for equal pixels in any process; equality and hashing use the id, so a diff never scans the pixels. The initialiser is failable (a dimension that is not positive, or a byte count that is not `width * height * 4`, gives nil). `ImageReference.pixels(RGBAImage, scale:)` carries it through `ImageSpec` and the resolved node (`node.image`); a scale that is not positive is 1. The intrinsic size is pixels / scale in points, computed in `computeSize` with no host hook (the hooks `imageIntrinsicSize`, `imageFitIntrinsicSize` and `imageFontIntrinsicSize` are system-symbol hooks and are skipped for pixels, which the environment font never resizes). The image is not resizable until `.resizable()`; `.resizable().scaledToFit()` and `.frame` use the existing image layout paths. The semantic role is image, the label the node's own accessibility label (a decorative image has none: on the Mac SwiftUI hides an `Image(decorative:)` from the accessibility tree unless it is wrapped in `.accessibilityElement(children: .ignore).accessibilityLabel(..).accessibilityAddTraits(.isImage)`, which the cases do, around the Image and inside any `.frame`; wrapping the framed view reports the frame on Windows and the image on the Mac).

F18. **The decoder is Swift, with no zlib or system library (round 5 block 35).** `ImageDecoder.decode(_:maxPixel:)` (host, `ImageDecoder.swift`, `PNGDecoder.swift`, `Inflate.swift`) reads PNG gray 1/2/4/8/16, gray+alpha 8/16, RGB 8/16, RGBA 8/16 and palette 1/2/4/8, tRNS (palette alpha, and the gray and RGB colour keys), all five filters, stored, fixed and dynamic deflate. It checks every chunk CRC, the zlib header and Adler-32, chunk order, sizes (at most 2^26 pixels), palette indices and the data length, and throws a typed `ImageDecodeError` (`notAnImage`, `truncated`, `corrupt`, `unsupported`), never a blank image. Adam7 interlace is refused as `unsupported("Adam7 interlaced PNG")`. sRGB, gAMA, cHRM, iCCP and every other ancillary chunk are ignored (no colour management: stored sample values are the output values), an unknown critical chunk is refused; 16-bit samples round to 8 bits as (v * 255 + 32767) / 65535 (not compared with Apple: no 16-bit case is paired). The ICO reader takes the directory entry whose longer side is the smallest one at least `maxPixel`, else the largest (a tie goes to the higher bit depth, then the earlier entry); a PNG entry goes through the PNG decoder, a BMP entry (1, 4, 8, 24, 32 bit, uncompressed, BITMAPINFOHEADER, up to 1024 px) through the DIB reader with its AND mask (a 32-bit entry with any alpha ignores the mask). An image whose longer side is over `maxPixel` is then reduced by an area-weighted box filter on premultiplied alpha (a transparent pixel's colour never bleeds in), aspect kept, rounded size, never upscaled; `maxPixel <= 0` means no limit. Tests: `ImageDecoderTests` (25 PNG fixtures written by Python zlib and struct: every colour type and depth, every filter, mixed filters, stored and dynamic deflate, tRNS, ancillary chunks; 11 corrupt inputs; every truncation; bit flips; ICO PNG, 32/24/4-bit DIB, size choice; downscale).

F19. **Painting registers the pixels once per content, size and opacity (round 5 block 35).** `ResolvedNodePainter` registers an image per (content id, painted device-pixel size, opacity as a byte) and paints `.image(handle, frame)` at the node's pixel frame; a later commit reuses the handle, a commit without the node releases it, a failed commit releases only the new ones, `releaseAll` releases all (same commit protocol as shape images). A frame smaller than the image (`.resizable().frame`, `scaledToFit`) is box-filtered to the frame's device-pixel size first, so the renderer samples 1:1 and a shrunk icon is not aliased; a frame larger than the image keeps the source pixels and the renderer scales it. Node opacity multiplies the alpha channel (the colour stays straight). Tiled (`resizingMode: .tile`) and cap-inset images are refused with `HostPaintError.systemImageContractMismatch`. The host logs one `PIXEL_IMAGE id=.. source=WxH registered=WxH xPX yPX widthPX heightPX alpha=` line per painted image.

F20. **Apple's PNG decode and blend are exact for sRGB-untagged 8-bit data, and the Windows paint equals them (round 5 block 35).** Measured on the Mac capture of `exact-opaque-v1` and `alpha-blend-v1` (macOS 27, ImageIO `CGImageSourceCreateImageAtIndex`, `Image(decorative:scale: 2.5)`, light, capture scale 2.5): against the decoded RGBA blended over white in floating point the largest difference over 1600 + 1600 + 6000 pixels of the opaque cases is 0, and over 3200 pixels with alpha 0 to 255 it is 0.50 level (i.e. Apple rounds the exact blend; colour management shifted nothing; a see-through pixel with a red colour and alpha 0 leaves white). Windows (`ImageDecoder` + `swr_image_register` straight alpha) is pixel-identical to the Mac over the whole 800 x 600 frame in all three cases (exact, no tolerance): P px at scale 2.5 is P / 2.5 pt and maps 1:1 to device pixels. Not measured against Apple: PNGs that carry an sRGB, gAMA or ICC chunk (the Windows decoder ignores them; Apple may convert), 16-bit data, Adam7.

F21. **A downscaled image is gated with a named tolerance, not exactly (round 5 block 35).** `scaled-down-v1` draws `.resizable().frame` and `.resizable().scaledToFit().frame` images at 2:1, 1.6:1, 4:3 and 2.5:1. Frame (the semantic tree, role image, name, bounds within 0.05 pt) and position (every pixel outside the images, and the image rectangles, are identical) match exactly; inside the images CoreGraphics' interpolation and the host's box filter differ: `pair.py` reports max 64 / 255 in 3766 pixels on the 1 px ring edges of a 40 -> 30 px palette image and on the checker/diagonal image (<= 43), <= 3 on smooth gradients (N=1). The case carries `edgeAATolerance` 64 with that reason (decision 5 style; the edge band is derived from the Mac image, out-of-band pixels stay exact). Candidate kernels were compared offline against the Mac capture (Pillow): a bilinear kernel measured 48 on the ring image, bicubic 54, Lanczos 56, box 64 (an area box that is not Pillow's box); no kernel matched, so the box filter stays (deterministic, no overshoot). N=20 evidence is needed before the 64 is treated as the bound.

F22. **What block 35 does not deliver.** Adam7 PNG; JPEG, GIF, WebP, BMP files and ICO entries that are 16-bit, compressed or BITMAPV4/V5 with bit fields; PNG colour management (sRGB/gAMA/iCCP); `Image(_ cgImage, scale:, label:)` (a labelled, non-decorative image), `.renderingMode(.template)`, `.interpolation(_:)`, `.antialiased(_:)`, orientation, tiled and cap-inset resizable images (refused visibly); image under `.opacity` is implemented and unit-tested but has no paired case (decision C10); the Pulse side (`HubImage` Windows backing) is applied by that session.

## 2026-10-15: wave 0 lane I1, the image decode service (`factory/pipeline/blocks-w0-i1`, `factory/tools/image-io`; decisions G30-G39)

Sources fetched 15 October 2026: Microsoft Learn `IWICColorTransform` (https://learn.microsoft.com/en-us/windows/win32/api/wincodec/nn-wincodec-iwiccolortransform: a transform maps an `IWICBitmapSource` between colour contexts and cannot be reinitialised), "How-to re-encode a JPEG image with metadata" (https://learn.microsoft.com/en-us/windows/win32/wic/-wic-codec-jpegmetadataencoding: `CreateDecoderFromStream`/`CreateDecoderFromFilename` with `WICDecodeMetadataCacheOnDemand`, `GetFrameCount`, `GetFrame`), design `docs/foundations-images-fonts.md` S1 (built-in codecs). G31. **I0, the Mac capture path is sRGB, and CoreGraphics clips (measured on macOS 27.0.1, build 26A434; `factory/tools/image-io/i0-capture-colourspace.swift`, result `factory/pipeline/blocks-w0-i1/evidence/i0-capture-colourspace.json`).** The capture path is the factory's own (an `NSHostingView` in a borderless offscreen window pinned to scale 2.5, `displayIgnoringOpacity` into an `NSBitmapImageRep` created with `.deviceRGB`, PNG written by `rep.representation(using: .png)`). 24 patches (neutral, primaries, mixed, saturated and dark colours) as one 960 x 40 px image, the same bytes tagged Display P3, sRGB, Adobe RGB and untagged (device RGB), drawn with `Image(decorative:scale: 2.5)`: (1) the captured bytes are in **sRGB**, whatever the image was tagged with: P3-tagged pixels come out as exactly the bytes CoreGraphics produces drawing the image into an 8-bit sRGB `CGContext` (largest difference **0** of all 72 values), and differ from the unconverted numbers by up to 50 (P3) and 64 (Adobe RGB); the same bytes tagged sRGB or untagged come out unchanged (difference 0). The written PNG carries the sRGB chunk (ImageIO reads it as `kCGColorSpaceSRGB`). (2) **No rendering intent changes anything:** default, perceptual, relative colorimetric, absolute colorimetric and saturation give byte-identical P3 -> sRGB and Adobe RGB -> sRGB results (largest difference 0 between each intent and the default). (3) **Out-of-gamut colour is clipped per channel** (P3 (255,0,0) -> sRGB (255,0,0); P3 (176,36,120) -> sRGB (192,0,122)): a colorimetric clip, no gamut mapping. So the Windows reference space is sRGB, untagged and sRGB-tagged images are unchanged, and the target of the ICC conversion is a clipping matrix/TRC conversion.

G32. **Contract of the service (measured against ImageIO, `factory/pipeline/blocks-w0-i1/expected/oracle.json`).** Pixels are 8-bit sRGB, straight alpha, top-left origin; `CGImage` on Windows is `SwiftRightRuntime.CGImage` (`width`, `height`, `bitsPerComponent` 8, `bitsPerPixel` 32, `bytesPerRow`, `alphaInfo` `.last` or `.noneSkipLast`, `colorSpaceName` "sRGB", `pixels: RGBAImage`); `Image(decorative: CGImage, scale:orientation:)` and `Image(_ cgImage:scale:orientation:label:)` exist on Windows only (the Mac uses SwiftUI's), `Image.Orientation` has the eight EXIF-ordered cases, `label:` is the accessibility label (`ImageSpec.labelText`). Measured rules the policy follows because the Mac does: **grey images (PNG, JPEG) are not colour converted** (ImageIO tags them Generic Gray Gamma 2.2 and drawing into sRGB returns every one of the 256 values unchanged); **a `gAMA` chunk without profile is ignored** (ImageIO: sRGB); **16-bit samples reduce with `round(v / 257)`** (matches all 4096 grey and 12288 RGB ramp samples; WIC truncates `v >> 8` for RGB and misses 16 of 4096 grey samples by one through its own gray -> RGBA64 conversion, so the host reads the native 16-bit grey, RGB48 and RGBA64 samples and reduces them itself); **RGB under alpha 0 is unspecified** (WIC keeps a GIF's palette colour, ImageIO zeroes it; the gate ignores it, the paint contract premultiplies); a 32-bit BMP without alpha mask is opaque, with a V5 alpha mask it has alpha (V4 headers: ImageIO returns nothing, WIC decodes them, equal to the V5 decode). `maxPixel` is the block 35 rule, area-average on premultiplied alpha, never upscaled.

G33. **ICC to sRGB: the WIC colour transform cannot match the Mac, so matrix/TRC profiles are converted in Swift (`ICCMatrixTRC`), the WIC transform is the fallback.** Measured on the Dell: `IWICColorTransform` from an embedded Display P3 profile to the EXIF sRGB context **gamut-maps** out-of-gamut colour (P3 (176,36,120) -> G = 21; the Mac clips to G = 0; up to 21 levels at P3 saturated colours) and the output is **byte-identical for every rendering intent written into the profile header** (0, 1, 2, 3, four sandbox runs), so no setting matches the Mac. Inside the gamut it differs by up to 3 levels. `ICCMatrixTRC` reads the profile's colorants and TRC (`curv` table or gamma, `para` types 0-4), linearises, multiplies through D50 XYZ to linear sRGB, clips, encodes with the sRGB curve in double precision and rounds: on the P3 PNG corpus it is within **1** level of CoreGraphics (Windows run: P3 RGB 8-bit: 40 of 480 pixels differ, by 1 in one channel; unit test `testMatrixTRCMatchesCoreGraphicsWithinOneLevelAndClipsLikeIt` on the Mac against CoreGraphics' own output). A profile with an A2B LUT, a grey or a CMYK profile, or one whose description names sRGB (skipped: nothing to convert) is not converted by it: sRGB-described profiles are left as they are, the others go through the WIC transform and are NOT gated. The profile is read with the codec (`IWICBitmapFrameDecode::GetColorContexts`, type `WICColorContextProfile`); EXIF colour space contexts are not converted.

G34. **Named tolerances (`factory/pipeline/blocks-w0-i1/tolerances.json`; the maximum absolute difference per channel and the largest per-channel mean over the image, Windows against ImageIO, rounded up once).** JPEG decode: baseline and progressive 4:4:4 max 3, mean 0.25 (the IDCT alone); 4:2:2 max 3, mean 0.6; 4:2:0 max 16, mean 1.1 (chroma upsampling differs; the maximum is on hard colour edges); grey max 1, mean 0.05; progressive equals baseline in both decoders; P3 JPEG max 3, mean 0.3; P3 PNG max 1, mean 0.09. All other lossless cases are **byte-exact** (below). The tolerances are measured on the corpus and the calibration set is the gating set (one set, stated: the design's separate-sets rule belongs to the resampling filter fit in I2).

G35. **CMYK JPEG differs a lot from the Mac and is gated only by a named wide tolerance (max 58, mean 14.1, red channel).** ImageIO converts through its colour-managed Generic CMYK; WIC's JPEG decoder yields CMYK that the format converter turns into RGB with a plain formula. No published profile reproduces the Mac conversion, so it is not fitted; CMYK JPEG is rare in the hub's use. A product that needs Mac-identical CMYK has to supply the conversion.

G36. **Corrupt and truncated input throws, and the policy, not the codec, guarantees it.** `ImagePolicy.checkComplete` walks the container (PNG: every chunk with its CRC up to IEND; JPEG: markers to EOI after a scan; GIF: up to the end of the first frame; BMP: header size against the pixel data; ICO: every directory entry inside the file) and `ImageDecodeError` is `notAnImage`, `truncated`, `corrupt` or `unsupported` (WIC HRESULTs map: `0x88982F50`/`F07` -> notAnImage, `F72` -> truncated, `F60`/`F61`/`F70`/`F62`/`F51` -> corrupt, `F80` -> unsupported). Evidence from the 25 negative controls: **WIC alone returned an image for 11 of them** (truncated PNG with and without IEND, truncated Adam7, JPEG cut in the scan, without EOI, progressive, CMYK, a destroyed first marker, a cut GIF, an ICO with a missing entry, an ICO entry claiming 100 MB; it also writes libjpeg warnings such as "Corrupt JPEG data: premature end of data segment" to stderr), **ImageIO returned an image for 10**; the service throws for all 25. A frame is never delivered unless the container is complete.

G37. **Entry choice, orientation and thumbnails are policy, not codec.** ICO: the block 35 rule (smallest entry at least `maxPixel`, else the largest; ties to the higher bit depth, then the earlier entry) over the directory parsed in Swift; the frame is matched to the entry by size and order (ImageIO orders entries differently; same-size entries cannot be told apart by their properties, so the tie rule is a unit test and `ico-tie` is decoded only). EXIF orientation 1-8 is read in Swift (JPEG APP1, PNG eXIf, TIFF IFD0) and applied as pixel moves (`RGBAImage.oriented`), so neither codec's behaviour matters: ImageIO and WIC both return the stored orientation. Gated byte-exact in the lossless PNG eXIf carrier (8 of 8) and within the 4:4:4 JPEG tolerance in the JPEG carrier (8 of 8); every file shows the same upright picture. **Thumbnails** use the host's box filter on both platforms (identical buffers on the Mac and Windows); against ImageIO's own thumbnail filter they differ by up to max 98, mean 23.2 per channel (alpha edges of 8 px thumbnails); the real resampling tolerance is I2's (1.4).

G38. **Mac deviations the Windows service does not copy.** (a) ImageIO ignores the AND mask of a 24-bit ICO DIB entry (alpha 255 everywhere); WIC and the block 35 decoder apply it (the 4-bit and 8-bit palette entries are masked by ImageIO too): those two cases are gated against the block 35 decoder (exact), reason in the manifest. (b) ImageIO returns premultiplied pixels for grey+alpha, 16-bit alpha, V5 BMP and P3 with alpha: the Mac oracle for those is lossy at partial alpha, so they are compared opaque-exact and partly transparent premultiplied (within 1; all measured at 0); the Mac backend of `SwiftRightImageIO` has the same limit for those formats, which the Mac's own drawing does not show.

G39. **Not delivered or not proven.** (1) No pixel-capture gate (buffers only, by design); the hub icon path (`HubPlatformServices.decodeImage`, painter use of `ImageDecoder.resample`) is unchanged. (2) WIC colour transform path is unreached by the corpus and ungated (LUT/grey/CMYK profiles). (3) TIFF, HEIC/WebP/AVIF are recognised only (TIFF sniffed, decoded if WIC does; no case). (4) `Image(_ cgImage:...label:)` accessibility label is tested in the runtime on the node, not on a Windows capture. (5) Windows 10 and other Windows builds were not decoded (one Dell, build 26100 / the Sandbox's WindowsCodecs); codec updates through Windows Update can change JPEG results by a level and reopen G34. (6) The Mac oracle binds to macOS 27.0.1; a macOS upgrade reopens it (design 5). (7) Animated GIF frames beyond the first, EXIF colour space contexts, embedded thumbnails and HDR formats are out of scope. (8) The old decoder was not deleted (see the deletion plan).

H17. **An explicit render scale is a public, general capability of the window: ABI 0.10 carries it, `Bridge.run(renderScale:)` and `HostWindowOptions.renderScale` expose it (coordinator decision, 16 October, after Sage's rules).** Why now: GitHub's windows-2025 runners have a Hyper-V display (1024x768 maximum, 125% maximum per-monitor scale; mode enumeration fails with Win32 error 203), so the factory's Windows captures could not run at the scale 2.5 (240 dpi) that every gate was fitted at (CI runs 38838553928, 38839279687, 38839728447; `factory/tools/ci/dpi-probe.ps1`). The capability is not a test hook: it is an explicit device scale factor like Chrome's `--force-device-scale-factor`, `QT_SCALE_FACTOR` or SwiftUI's `ImageRenderer.scale`. Real uses: fixed-scale exports, and the same rendering on every display.

- **API.** `Bridge.run(title:width:height:pointerMoves:renderScale:)` (SwiftRightBridge, `renderScale: Float? = nil`) and `Bridge.run(_: HostWindowOptions)` (SwiftRightHost, `HostWindowOptions.renderScale`). `Bridge.supportsRenderScale` is true on a 0.10 renderer; a scale on an older renderer, or outside [0.25, 16], or not finite, makes `run` throw (never silently dropped). Debug and release behave the same; nothing is gated by build configuration, environment variable or name.
- **ABI.** 0.10 is additive and follows the 0.9 pattern. New exports `swr_bootstrap_query_v10` and `swr_get_api_v10` (the 0.8 table, 22 functions, unchanged; the legacy, `_v07`, `_v08` and `_v09` exports still describe 0.6 to 0.9). `swr_run_options_v10` (48 bytes) is the 40-byte options plus `float render_scale` at offset 40 and a reserved word; a host sends `struct_size >= 48` to supply it, and 0 means none. `swr_bootstrap_info_v10` (136 bytes) is the 0.9 view plus `run_options_v10_size` (48). The renderer refuses (SWR_E_BAD_ARG, before any state changes) a non-finite, negative or out-of-range scale. A host that sets no scale sends the 40-byte struct it always did.
- **One scale source.** Let S be the render scale and G the scale GPUI itself uses (the window's DPI / 96). Without an override S == G and every code path is the one it was (`effective_scale` is the previous `dpi / 96` expression, and the text ratio k = S / G is exactly 1.0, so the shaping call, the cache key and every product are unchanged). With an override S replaces `GetDpiForWindow`-derived scale wherever the host or the renderer reads a scale: `view.rs` `launch` (initial metrics), `read_client_metrics` (the ready-time re-read) and `paint_root` (metrics event); `swr_window_get_metrics` and `EV_WINDOW_METRICS` report S; the Swift bridge replaces `MeasureRequest.scale` with S (`Bridge.measure`), so the host's measurement scale, font and text metrics, and everything it lays out use S.
- **Window size.** GPUI turns the logical size it is given into device pixels with G, so the renderer asks for `dip * S / G` logical (G read from the primary monitor before the window exists) and the client area is `dip * S` px. The render log line `render-scale ready: client WxHpx expected WxHpx matches=...` records the settled check at ready (the hidden window's first client rect is an early sample).
- **Text.** GPUI rasterises glyphs at logical size times G. With an override the renderer shapes at `font_size * k` (k = S / G), converts every layout value it reads back to physical pixels with G (so with k, glyphs are `font_size * S` px), hands GPUI `line_height * k` and tracking `* k` at paint, and keeps the host-facing DIP values (line height, tracking, baselines) at S. The measure cache key includes k when it is not 1.
- **Hit-testing, pointer mapping and UIA.** All three work in physical pixels of the window, which the size above makes a `dip * S` grid. GPUI's logical pointer position times G is that physical pixel, and the painter divides host rectangles by G; the two are inverses (`scale.rs` `pointer_mapping_round_trips`). AccessKit bounds are the host's physical rectangles with no conversion (`ax.rs` `uia_bounds_are_the_host_physical_rectangle_at_any_scale`). Nothing there reads a DPI.
- **WM_DPICHANGED under an override: the scale stays S.** GPUI handles the message itself (it resizes to the OS suggestion at the new G). The renderer then reports the new physical size with the unchanged S in `EV_WINDOW_METRICS`, drops its shaping cache (shaped text baked in the old k) and queues the event once more even if no number moved, so a host re-measures on it. A retained text run shaped before the change keeps the old k until the host re-measures. Nothing re-derives S from the new DPI. Without an override WM_DPICHANGED is exactly what it was.
- **The harness only passes the value.** The factory capture-host template passes 2.5 through `Bridge.run(renderScale:)`; it has no scale logic and no environment parsing. On the 240 dpi sandbox 2.5 is the display's own scale, so k is exactly 1 and the captures are expected to be identical to the no-override ones.
- **Proof status.** Unit tests: Rust `scale.rs` (parse, effective scale, window size on any display, pointer round trip), `ax.rs`, `lib.rs` (cache key, v10 bootstrap); Swift `RenderScaleTests` (layout, negotiation, no-override equals the old options, measurement scale, metrics latch) and `HostWindowOptionsTests`. The Dell and CI results are in the round record below the renderer provenance in `factory/pipeline/blocks-37-38/README.md`.

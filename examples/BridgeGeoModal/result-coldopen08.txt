DEFINITIONS (both measured on the QueryPerformanceCounter clock, one system-wide clock for host and driver)
  M1  main-queue blocking during open. A producer thread posts a job to the main dispatch queue every 2 ms. For an open requested at req, M1 = the largest (ran - enqueued) of the jobs enqueued in [req, req + 150 ms).
      This is what Modal06 reports as modal_open_one_off. It measures how long the UI thread could not run queued work around the open. It does not say when the dialog appeared.
      M1gap = the longest pause between consecutive job RUNS in [req - 10 ms, req + 300 ms] (cross-check of M1).
  M2  request -> dialog visible. The host logs req_ns just before the bridge request. The driver stamps, from a WinEvent hook on the host process, the first EVENT_OBJECT_SHOW of a #32770 window
      (dialog) or EVENT_SYSTEM_MENUPOPUPSTART / EVENT_OBJECT_SHOW of a #32768 window (menu). M2 = stamp - req_ns. (M2win in the tables.)
      M2uia = request -> first UI Automation WindowOpened (dialog) or MenuOpened (menu) event, measured only in the "coldat" runs, where a UIA client is subscribed. It is when an accessibility client is told, not when the window exists.

FINDINGS
  1. Dialog (TaskDialogIndirect) is the slow modal; the menu is not. Cold dialog: M1 median 37.3, max 45.6 ms (0 of 20 above 50); M2 median 43.1, max 54.1 ms (2 of 20 above 50: 50.32 and 54.08).
     Cold menu: M1 median 6.9, max 8.8 ms; M2 median 7.0, max 7.8 ms.
  2. Warm dialog: M1 median 28.1, max 32.5; M2 median 33.4, max 37.3. Cold costs about 9 ms more than warm at the median (37.3 vs 28.1); the fastest cold dialog was 31.5 ms and the fastest warm one 23.4 ms, so most of the cost is the dialog's own creation, not first-use initialisation.
  3. For a dialog, M2 - M1 is 4.5 to 8.5 ms in every cold run (median 6.0). The UI thread is blocked for almost exactly the time it takes the dialog to appear, so M1 and M2 are nearly the same number for dialogs. For a menu M2 - M1 is about 0: the menu opens with almost no main-queue blocking.
     The earlier tuple 08 Modal06 figure (per-run maxima 29.30 to 39.59 ms over 20 runs of 6 modals each) is consistent with this: it is the max over a menu, a dialog and four more, and only the first menu of a run is process-cold.
  4. With a UIA client attached (coldat): menu unchanged (M1 max 7.2 ms); dialog M1 median 35.2, p90 44.2, max 65.4 ms (1 of 10 above 50: 65.36, M2 73.71). Ten runs are too few to separate a UIA effect from the spread seen without it (cold max 45.6). Treat 65 ms as a possible outlier of the same family as tuple 07's single 60.9 ms.
     M2uia is 139 to 248 ms for a dialog and 24 to 34 ms for a menu: UIA event delivery lags the window by 100 to 200 ms for dialogs; it is a notification latency, not the time the dialog is on screen.
  5. The 50 ms bound has little headroom for a cold dialog: max 45.6 ms (91% of the bound), 4.4 ms margin, and across tuples 07 and 08 plus this run the dialog has been seen at 60.9 (tuple 07), 65.4 (UIA attached) and 45.6 (cold, no UIA) ms.

PROPOSED CRITERION (the 50 ms bound itself is unchanged; this only says what it applies to; the decision is Adrian's)
  A. Name the measure in the contract: "modal_open_main_queue_blocking" = M1 as defined above, per modal kind. Retire the name modal_open_one_off for the aggregate over all six Modal06 scenarios, which mixes cold and warm opens.
  B. Measure it on fresh processes, first modal only: at least 20 runs per kind (dialog and menu), cold condition, no AT client, same host/driver as here (scripts/drive-coldopen.ps1). Report min / median / p90 / max and every run.
  C. Pass rule at the unchanged 50 ms: median <= 50 ms and p90 <= 50 ms, and no single run above 75 ms (1.5 x the bound), over those 20 runs. With this data: dialog median 37.3, p90 43.0, max 45.6 -> pass; menu max 8.8 -> pass. A strict "every run <= 50 ms" rule also passes here (45.6) but would fail on tuple 07's 60.9 and on the UIA run's 65.4,
     which are single outliers in a population whose median is 37 ms; the 1.5 x ceiling still fails a run that is truly bad (a stalled modal blocks the queue for the whole modal, over a second: the lost-wake defect of Modal06 runs 15 and 20 ran its jobs in one burst just before the result).
  D. Keep the existing in-run Modal06 checks (steady p99 <= 16.7 ms, run gap <= 100 ms, pump counts) unchanged.
  E. Report M2 (request -> visible) beside M1 as the user-facing number. Observed: dialog max 54.1 ms without a UIA client, 73.7 ms with; menu max 7.8 ms. No M2 bound is derived from this data; if one is wanted, it is a new decision (a bound of 100 ms would have >= 26 ms headroom on these data; 100 ms is a proposer's convention, not a number from this repository).
  F. Not covered and still open: cold-boot first launch (cold disk and shader/font caches), a second machine or lower-end GPU, an AT client with a real screen reader (NVDA, Narrator), and whether the dialog creation cost (TaskDialogIndirect, comctl32 v6) can be reduced (a custom dialog would change the contract, not the bound).

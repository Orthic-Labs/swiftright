# Blocks 11 (swiftui.button) and 16 (swiftui.list), SR1 round 3 lane A

`make_cases.py` writes every case (`new-case.py`: package/ + mac-source/ with a byte-identical Witness.swift, plus pair.json with the gate and the interaction steps); `run-n20.sh <stage> [runs] [case...]` runs the pairs on one staged product build (`python3 factory/tools/stage-product.py`, renderer 0.7 `82513ae0` is pair.py's default).

## Hosts

- **Windows** (`shared-windows-host`): the shared capture host plus input routed to the runtime as a user's would be. A pointer press arms the node under the pointer, the release on the same node is the click: a Button runs, a List row selects (shift/ctrl extend). Keys: Return/Escape/characters run `keyboardShortcut`s, Tab moves focus, Up/Down move a List selection, Delete removes the selected rows (`onDelete`), PageUp/PageDown move the selected row one place (`onMove`, the model route: a drag is not driven; modifier keys cannot be used because the F2 job's `Get-Vk` is shadowed by its `$vk` variable). Every bridge event is printed as `HOST_EVENT`. A List selection paints in the accent colour once the keyboard is in the list (a click on a row, an arrow key), grey before (`ResolvedNodePainter.listIsActive`).
- **Mac** (`shared-mac-host`): an `NSHostingView` in a window that is never ordered onto a screen, drawn at scale 2.5 into 800 x 600 px, with `--steps` (the Sandbox step vocabulary: click, key, char, invoke, wait, dump, shot). Measured on macOS 27: AppKit drops synthetic mouse events for a window that is not on screen, so a `click` presses the Button under the point through its accessibility element (`accessibilityPerformPress`, in-process, no permission) or selects the table row under it (and makes the table first responder, as a click does); `key` goes to the table (`keyDown` for the arrows, `interpretKeyEvents` for Delete, which is how SwiftUI's `onDelete` hears it) or to the window's key equivalents (a Button's `keyboardShortcut`, Return for the default button). **onMove without a drag:** SwiftUI's List reorders through its `NSOutlineView` data source (`validateDrop` / `acceptDrop`), which wants a live dragging session; a session cannot be made without a drag image on screen, so the host hands SwiftUI a stand-in session and `NSDraggingInfo` (`FakeDragSession`, `FakeDragInfo`) and delivers the drop a drag would: `onMove` gets exactly the offsets and destination SwiftUI computes. `list-NN.json` (written beside `ax-NN.json`) lists the table's rows (text, selected, frame) because SwiftUI's accessibility tree publishes list rows without roles.

## Gates

- `pair_button_report.py` (`buttonGate`): bordered, prominent and default-action buttons (same height and y, both 28 px caps edge-aa 32, flat bands, label centred, label ink colour within 40 of the Mac's; the width follows the label, decision 2).
- `pair_textcolour_report.py` (`textColourGate`): borderless and plain buttons (no body: the label's ink colour; glyph pixels excluded by name).
- `pair_semantic_report.py` (`semanticGate`): the click and Return cases (tree: `Count n` text, `Add` button) with exact counter squares.
- `pair_list_report.py` (`listGate`): rows (count, text, order, selected flag, frame) from the Mac table against the Windows UIA list items, label ink colour per row; pixels by pair.py (exact or edge-aa 32 outside the named row-label regions).
